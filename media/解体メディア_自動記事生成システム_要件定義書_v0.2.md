**運営主体**：GENBABOXX
**作成日**：2026年8月1日

開発担当者への引き渡しを前提とした要件定義書。ヒアリング資料をもとに、確定済みの方針を反映して具体化したもの。未確定事項は第15章に集約している。

| 項目 | 決定内容 |

## 1. プロジェクト概要

### 1.1 目的

解体業界の実務者向け専門メディアを新規構築し、AIによる記事の自動生成・自動公開を行う。検索流入を獲得し、最終的にBAKUSOQへの問い合わせ・資料請求につなげる。

### 1.2 既存サイトとの関係

BAKUSOQ公式サイトとは独立したドメインで運用する。GENBABOXXが運営する専門メディアとして位置づけ、記事内および記事末尾でBAKUSOQを自然に紹介する。

### 1.3 成功指標（初期6か月）

- 公開記事数：150本以上
- 品質チェック合格率：80%以上
- 検索流入：月間1,000セッション以上
- 問い合わせ・資料請求：月間3件以上

## 2. 記事内容ポリシー

### 2.1 数値不使用ポリシー（最重要）

本システムの品質担保の中核。AIによる数値の幻覚を構造的に排除する。

**禁止する数値表現**

- 金額（円、万円、千円）
- 重量・容積（t、kg、m³）
- 単価表現（〜円/t、〜円/㎡、〜円/人日）
- 割合（%、割）
- 期間の断定（工期は◯日、など）

**許容する数値表現**

- 年月日、法令の施行時期
- 法令の条番号、政令番号
- 出典URLが併記された公的統計値（初期リリースでは原則使用しない）
- 一般名詞化した規格値（4t車、0.25m³級バックホウ など）

### 2.2 数値を使わずに独自性を出す記事の型

すべての記事は以下3種のいずれかに分類される。

| 型 | 内容 | 主なカテゴリー |
|---|---|---|
| A：手順・チェックリスト型 | 実務上の判断順序と確認項目を示す | 見積もり、原価管理、工期 |
| B：計算テンプレート型 | 計算式と項目構成のみ提示し、単価は読者が入力する前提で書く | 原価管理、人工、産廃 |
| C：一次情報型 | 法改正・制度・補助金。**出典URLの併記を必須とする** | 法改正、補助金、業界ニュース |

## 3. システム構成

```
[GitHub Actions（毎日定時実行）]
        ↓
[記事生成バッチ（Node.js / TypeScript）]
        ↓  ← マスタ情報・生成設定を取得
[AI API（記事構成 → 本文 → 修正）]
        ↓
[品質チェック（3層判定）]
        ↓
[Supabase へ登録（公開 or 下書き）]
        ↓
[Next.js フロントサイト] ← [Cloudflare Pages で配信]
        ↑
[自作管理画面 /admin（Supabase Authで保護）]
```

### 3.1 技術選定

| 領域 | 採用 | 補足 |
|---|---|---|
| フロントサイト | Next.js（App Router） | ISRで記事ページを静的化 |
| ホスティング | Cloudflare Pages | 無料枠が商用利用可。Vercel Hobbyは非商用扱いのため不採用 |
| データ基盤 | Supabase（PostgreSQL + pgvector） | 記事、テーマ、CTA、マスタ、生成履歴、ログ、ベクトル類似度判定 |
| 記事編集・運用 | 自作管理画面（/admin） | Supabase Authで保護 |
| 定時実行 | GitHub Actions | cron設定。無料枠内で完結 |
| AI | Claude API または OpenAI API | モデルは第15章で確定 |
| 画像 | カテゴリー別固定テンプレート（SVG→PNG生成） | タイトルのみ差し替え |

### 3.2 選定理由の要点

- **Vercel無料プランは事業用途に使わない**：Hobbyプランは個人の非商用プロジェクト向けの規約であり、法人メディアでの利用は規約違反となる可能性が高い。
- **Supabaseに一本化する**：重複判定にpgvectorが必要なためSupabaseは必須であり、ヘッドレスCMSを併用するとデータが2か所に分かれる。記事とその品質チェック結果を同一画面で突き合わせられなくなるため、記事本体もSupabaseに持つ。月額費用とAPI数制限も回避できる。
- **バックアップは自前で持つ**：Supabase無料プランには自動バックアップがない。週1回、記事データをJSONでエクスポートして保管する処理を定時実行に含める。

## 5. 自動生成パイプライン

### 5.1 処理フロー

```
1. 定時起動（GitHub Actions）
2. 自動生成の有効/無効を確認 → 無効なら終了
3. テーマ在庫から未使用テーマを1件選定（優先度順）
4. 過去記事との重複チェック（テーマ・タイトルのベクトル類似度）
5. 記事構成の生成（型A/B/Cのテンプレートを適用）
6. 本文の生成
7. SEOタイトル・メタディスクリプションの生成
8. 品質チェック（第6章）
9. 不合格 → AI自動修正 → 再チェック（最大2回）
10. 合格 → 公開トグルの状態に従い「公開」または「下書き」で登録
11. 2回修正しても不合格 → 下書き保存＋エラーログ記録
12. アイキャッチ画像の生成・付与
13. 生成履歴をDBに保存
14. 実行結果を通知（Slack または メール）
15. 週1回、記事データをJSONでエクスポートしてバックアップ（別ジョブ）
```

### 5.2 テーマ選定ロジック

- テーマは事前登録制（自動で無限に生成させない）
- `themes` テーブルから `status = 未生成` かつ `priority` が高いものを選定
- 直近30本と同一カテゴリーが3本以上続く場合は、別カテゴリーを優先
- 在庫が20件を下回ったら管理者に通知

### 5.3 AI呼び出し設計

各ステップを独立したAPI呼び出しに分割する（1回で全部書かせない）。

| ステップ | 入力 | 出力 |
|---|---|---|
| 構成生成 | テーマ、記事型、対象読者、見出し数、マスタ情報 | 見出し構成（JSON） |
| 本文生成 | 構成、文体設定、禁止表現リスト、数値不使用ルール | 本文（Markdown） |
| SEO生成 | 記事タイトル、本文冒頭 | SEOタイトル、メタディスクリプション |
| 自動修正 | 本文、不合格項目の一覧 | 修正後の本文 |

**プロンプトはコードに直書きせず、`prompts` テーブルから取得する。**

## 6. 品質チェック仕様

判定を3層に分け、AIに任せる範囲を最小化する。

### 6.1 第1層：機械判定（コードで確定判定）

| 項目 | 判定方法 | 不合格時 |
|---|---|---|
| 数値表現の混入 | 正規表現で金額・重量・単価・割合を検出 | **即NG（最優先）** |
| 文字数 | 設定値の下限・上限 | NG |
| 見出し構成 | H2/H3の階層が崩れていないか | NG |
| 禁止表現 | マスタの禁止表現リストと突合 | NG |
| CTA設定 | CTAブロックの有無 | NG |
| 画像設定 | アイキャッチの有無 | NG |
| SEOタイトル長 | 全角32文字以内 | NG |
| メタディスクリプション | 設定有無、全角120文字以内 | NG |
| リンク死活 | 記事内リンクにHEADリクエスト | NG |
| 出典URL（型Cのみ） | 出典の記載有無 | NG |

**数値検出の正規表現例**

```
金額：      /[0-9０-９,，]+\s*(円|万円|千円|億円)/
重量・容積： /[0-9０-９.．]+\s*(t|トン|kg|キロ|m3|m³|立米)/
単価：      /[0-9０-９,，]+\s*円\s*\/\s*(t|kg|㎡|m2|人日|台|日)/
割合：      /[0-9０-９.．]+\s*(%|％|割|パーセント)/
```

除外リスト（誤検知を防ぐため許可する表現）を別途マスタで管理する。例：`4t車`、`0.25m³級`、`第◯条`、`令和◯年`。

### 6.2 第2層：類似度判定（ベクトル検索）

- 記事タイトルと本文の埋め込みベクトルを生成し、Supabase の pgvector に保存
- 過去全記事との**コサイン類似度**を算出
- タイトル類似度 0.90 以上 → NG
- 本文類似度 0.85 以上 → NG

閾値は運用しながら調整できるよう、設定値としてDBに持つ。

### 6.3 第3層：AI判定（定性評価のみ）

以下の3点に限定してAIに評価させ、5段階でスコアを返させる。

1. 文章として不自然な箇所がないか
2. 論理の飛躍や矛盾がないか
3. 実務者にとって具体性のある内容か

いずれかが3点未満で不合格。**事実の正誤判定はAIに行わせない**（自己採点は機能しないため）。

### 6.4 判定結果の扱い

| 結果 | 処理 |
|---|---|
| 全層合格 | 公開トグルの状態に従って公開または下書き |
| 不合格（1回目・2回目） | 不合格項目を渡して自動修正 → 再チェック |
| 不合格（3回目） | 下書き保存、エラーログ記録、管理者へ通知 |

## 7. 管理画面 要件

すべて自作する。画面ごとの詳細は別紙「管理画面 仕様書」を参照。

### 7.1 記事・コンテンツ管理

- 記事一覧（フィルタ、ソート、検索、一括操作、不合格項目のタグ表示）
- 記事編集（タイトル、本文、見出し、画像、カテゴリー、タグ、URL、SEO情報、公開日時）
- 公開／非公開の切り替え
- カテゴリーの追加・編集
- CTA（見出し、本文、ボタン文言、リンク先、表示位置）
- 固定文言（BAKUSOQ紹介文、運営会社紹介文、免責文、記事末尾定型文）
- マスタ情報（用語集、FAQ、禁止表現、推奨表現、BAKUSOQ機能説明）

### 7.2 生成・運用管理

| 機能 | 内容 |
|---|---|
| 自動生成トグル | **完全自動公開 ON/OFF**、生成自体の一時停止 |
| 生成設定 | 文字数、文体、対象読者、見出し数、記事型の配分、公開時間、自動修正回数の上限 |
| プロンプト管理 | 構成生成・本文生成・修正の各プロンプトを編集 |
| テーマ管理 | テーマ一覧、優先度設定、除外設定、狙うキーワード、在庫数表示 |
| 品質基準設定 | 各チェック項目の閾値、有効／無効 |
| 生成履歴 | 生成日時、使用プロンプト、初稿、最終稿、チェック結果、修正回数 |
| エラーログ | 失敗記事の一覧と原因 |
| 利用状況 | API呼び出し回数、推定利用料 |

## 8. データモデル（Supabase）

```sql
-- 記事テーマ在庫
themes (
  id, title, category, target_keyword, article_type,  -- A/B/C
  priority, status,                                    -- 未生成/生成済/除外
  created_at, generated_at
)

-- 生成履歴
generation_logs (
  id, theme_id, cms_article_id,
  prompt_structure, prompt_body, prompt_fix,
  draft_first, draft_final,
  revision_count, status,                              -- 公開/下書き/失敗
  error_message,
  ai_model, input_tokens, output_tokens, estimated_cost,
  started_at, finished_at, published_at, published_url
)

-- 品質チェック結果
quality_checks (
  id, generation_log_id, revision_number,
  layer,                                               -- 1/2/3
  check_item, result, detail, created_at
)

-- 記事ベクトル（重複判定用）
article_embeddings (
  id, cms_article_id, title_vector, body_vector, created_at
)

-- 生成設定
settings (
  key, value, value_type, description, updated_at
)
```

## 11. 運用フロー

### 11.1 記事ステータス

| ステータス | 説明 |
|---|---|
| 自動公開 | チェック合格かつトグルON |
| 下書き | チェック不合格、またはトグルOFF |
| 公開停止 | 人が手動で非公開にした記事 |
| 生成失敗 | パイプラインがエラー終了 |

### 11.2 推奨する運用の立ち上げ方

システムとしてはトグル一つで切り替わるが、運用上は以下を推奨する。

1. **初期20〜30本**：トグルOFFで生成し、人が確認してから公開。どの品質チェック項目が実際に効いているか、閾値が適切かを実データで検証する。
2. **調整**：不合格パターンをもとに、プロンプト・禁止表現リスト・閾値を修正。
3. **移行**：合格率が安定したらトグルON。

## 12. エラー処理・通知

| 事象 | 処理 |
|---|---|
| AI APIエラー | 3回までリトライ（指数バックオフ）、失敗時はログ記録＋通知 |
| DB登録失敗 | 生成内容を一時退避し、通知。手動で再投入可能にする |
| チェック3回不合格 | 下書き保存＋通知 |
| テーマ在庫20件未満 | 通知 |
| 月間API利用料が上限超過 | 生成を自動停止＋通知 |

通知先はSlack Webhookを基本とする。

### 補足

最後の項目について。数値を使わない前提で、記事型A/B/Cに振り分けられるテーマが100本確保できるかは、開発と並行して早期に検証すべき事項。ここが埋まらない場合、公開頻度を週3本などに調整する判断が必要になる。
